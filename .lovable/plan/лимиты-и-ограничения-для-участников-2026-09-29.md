
# Лимиты и ограничения для участников

## Анализ вариантов

Разберём каждый тип лимита: зачем нужен, какие плюсы/минусы, и стоит ли включать в MVP.

| Тип лимита | Зачем | Минусы | Включаем? |
|---|---|---|---|
| **На конкретные модели** (whitelist) | Запретить дорогие/чувствительные модели джунам | — | Да (уже есть в Team) |
| **На типы (модальности)** text/image/video | Удобнее, чем перечислять модели; новые модели автоматом подпадают | Менее гранулярно | Да, добавить как «быстрый пресет» |
| **Лимит по токенам** | Знакомая метрика | Не сравним между моделями (Opus ≠ MJ), не работает для image/video (там per-request) | Да, но только для текстовых |
| **Лимит по $ / бюджет** | Единая валюта для всех модальностей, прямо отражает счёт | Цены могут меняться → лимит «плавает» | **Да — основной механизм** |
| **Интервалы (день/месяц)** | День ловит аномалии (утечка ключа), месяц — бюджет | Усложняет UI | Да: **день + месяц одновременно** |
| **Временное окно (с–по)** | Подрядчики, стажёры, демо-доступ | — | Да (необязательное поле) |

## Рекомендуемая модель

**Основа — $-бюджет**, токены оставляем как опциональный sub-limit для text-моделей. Логика:

```
у участника есть набор правил доступа:

1. Активность (active window)
   - valid_from / valid_until (оба опциональны)
   - вне окна → доступ заблокирован

2. Разрешённые модели
   - выбор по модальностям (text / image / video) — быстрые тоглы
   - + точечный whitelist/blacklist моделей внутри модальности

3. Бюджет в USD (главное)
   - daily_usd_limit    (по умолчанию пусто = без лимита)
   - monthly_usd_limit  (по умолчанию пусто = без лимита)
   - считается по тарифу из src/lib/pricing.ts (тот же, что в Billing)

4. Доп. лимит токенов (опционально, только для текстовых моделей)
   - daily_tokens / monthly_tokens
   - полезно, когда нужно ограничить «объём работы», а не деньги

Запрос пропускается, только если ВСЕ активные лимиты не превышены
(логическое И). Превышение любого → 429 + понятное сообщение, какой
именно лимит сработал.
```

### Почему $ как основной, а не токены
- Унифицирует text/image/video в одной шкале.
- Прямо привязан к счёту, который видит владелец в Billing.
- При смене тарифа лимит остаётся осмысленным (просто «потолок расхода»).
- Токены сохраняем как доп. рычаг для текстовых моделей, где это естественная единица.

### Почему день + месяц
- Месяц = бюджетная дисциплина.
- День = защита от инцидента (скомпрометированный ключ участника не сольёт весь месячный бюджет за ночь).

## Что меняется в UI

### Team → диалог «Настроить участника»
Перестроить текущий диалог в секции:

1. **Доступ во времени**
   - Switch «Ограничить срок действия»
   - При включении: два date-picker'а «с» / «по»

2. **Разрешённые модальности и модели**
   - 3 тогла: Текст / Изображения / Видео
   - Под каждым включённым — collapsible со списком конкретных моделей (галочки, по умолчанию все)

3. **Бюджет (USD)** — главная карточка
   - Поле «Лимит в день, $» (пусто = ∞)
   - Поле «Лимит в месяц, $» (пусто = ∞)
   - Под полями — живой прогресс «Использовано в этом месяце: $X из $Y» (mock-данные)

4. **Лимит токенов (опционально, advanced)**
   - Раскрывающаяся секция «Дополнительно: лимит токенов для текстовых моделей»
   - Поля «в день» / «в месяц»

### Карточка участника в списке
Заменить строку `Добавлен … · 500 000 токенов / мес · Моделей: 2/3` на компактные чипы:
`$50/день` `$1000/мес` `Текст +2 модели` `до 31.12.2026`
— показываем только заданные ограничения.

## Технические детали

- Расширить тип `TeamMember`:
  ```ts
  interface MemberLimits {
    validFrom?: string;       // ISO date
    validUntil?: string;
    modalities: { text: boolean; image: boolean; video: boolean };
    allowedModels: string[];  // whitelist внутри разрешённых модальностей
    budget: {
      dailyUsd?: number;
      monthlyUsd?: number;
    };
    tokens?: {                // только для text
      dailyTokens?: number;
      monthlyTokens?: number;
    };
  }
  ```
- Стоимость считается через существующий `costForRequest()` из `src/lib/pricing.ts` — единый источник истины с Billing и прайс-листом.
- Для MVP: всё хранится в локальном state `TeamPage` (как сейчас). Реальный enforcement — на стороне API; фронт показывает только UI настройки + mock-прогресс.
- Модели группируются по модальности через метаданные в `AVAILABLE_MODELS` (добавить поле `modality: 'text' | 'image' | 'video'`).

## Что НЕ делаем сейчас
- Реальный backend-enforcement (это серверная часть, отдельная задача).
- Алерты по email при достижении 80% лимита — добавим, если попросишь, после базового UI.
- Лимиты на уровне всей команды (только per-member) — можно вторым шагом.
